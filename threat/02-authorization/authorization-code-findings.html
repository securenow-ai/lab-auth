The headline: lab-auth is correctly authorized — every privileged route is role-gated, registration cannot set its own role, the role PATCH cannot be mass-assigned, it requires a fresh password (step-up), and a role change invalidates every session. The one real gap was blindness, not a hole: authorization decisions lived only in the app's own database, so a probe of the access-control boundary never reached SecureNow. That is now fixed (AZ-1), plus a race in the admin-quorum guard (AZ-2). Both shipped with tests.

Do we detect sudden privilege escalation? Yes — two ways:

  1. When a role is granted up (member → admin): the role_changed/direction=elevate event feeds

R-AZ-03 and the live 01-auth rule — the elevation is caught.

  1. When a boundary just opens with no role-change event (a mid-session grant, a replayed higher-privilege

session, or a gate regression): R-AZ-BOUNDARY catches the 403 → 200 on the same restricted route from traces alone, zero app code — validated live (/api/admin/users, 403 → 200).

Why 58 of 71 are N/A: lab-auth has no user-owned business objects (the dashboard is static, :365-379), no multi-tenancy, and no LLM-agent / MCP / tool-calling surface — so the object-level (BOLA), tenancy, and agentic groups have nothing to attack here. They are carried as forward-looking (§4).

1. The authorization model (as built)

Roles: member (1) < analyst (2) < admin (3) — the roles set + rank map (src/app.js, used :406/:417). Role lives on the users row, read fresh each request on session rehydrate (:121-133).

Gates: requireUser (:167) — any session · requireRole(...allowed) (:171) — role membership; on failure writes authorization.denied locally and now exports authz.denied to SecureNow (AZ-1, :174-181).

Write-path safety: registration inserts only id,email,name,password_hash — no role (:231-234); the role PATCH reads only validated role + :id, body never spread. No mass-assignment.

3. Findings

AZ-1 — Authorization decisions now exported to SecureNow · severity medium · 🟢 SHIPPED

Was: requireRole (:174) and the step-up gate (:409) recorded denials only in the local security_events table — SecureNow saw the 403 traces but not the authorization semantics (who, which role, which route, role-denied vs step-up). Function-level probing (OWASP API5) was undetectable *as such*.

Now (commit 609640f, src/app.js:174-181, :409-414): both denial points also emit('authz.denied', …) with decision, reason (role_denied / step_up_required), route, method, have_role, need_role, target_ref. emit is the lab's existing optional bridge (src/securenow-bridge.js).

// src/app.js — requireRole denial
emit('authz.denied', req, { userId: req.user.id, attributes: {
  decision: 'deny', reason: 'role_denied', route, method: req.method,
  have_role: req.user.role, need_role: allowed.join('|'), target_ref: req.params?.id ?? null,
} });

Backs detections: R-AZ-01 (validated: 3 routes, 18 denials) and R-AZ-02 (validated: 3 step-up blocks).

AZ-2 — Admin-quorum invariant + concurrent-role-change race · severity low · 🟢 SHIPPED

Was: self-demotion was blocked (:407), but two admins demoting each other concurrently were not serialized (TOCTOU, threats 56–57 / 44–48). A single-statement subquery would not close it under READ COMMITTED — its count takes no lock on the admin rows.

Now (commit 609640f, src/app.js:417-446): the role change runs in one transaction that locks the admin set FOR UPDATE, re-counts under the lock, and refuses any demotion that would leave zero admins (409 LAST_ADMIN, also exported as authz.denied reason=last_admin). A new integration test fires two concurrent cross-demotions and asserts exactly one 200 + one 409 and that one admin always remains (14 tests green).

Backs detection: R-AZ-03 — containment for the fan-out shape.

AZ-3 — Denial events carry no object owner (forward-looking) · severity low · 🟡

The authz events carry target_ref (the requested id) but not object_owner — fine today (no owned objects), but the day a GET /api/x/:id lands, true IDOR (caller ≠ object_owner on an *allow*) is detectable only if the event carries both. Add object_owner + emit on *grants* of sensitive resources then.

AZ-5 — IDOR on GET /api/notes/:id (owned object, predictable key) · severity high · 🟢 SHIPPED (found → detected → fixed)

Where. GET /api/notes/:id (src/app.js). The notes resource uses a predictable integer key (db/001_initial.sql), and the handler originally fetched the row by id only — never scoped to the caller: SELECT … FROM notes WHERE id=$1. Any signed-in user could read any note.

Why it matters. This is OWASP API1 / BOLA — the most common and most exploited access-control bug. A single IDOR request returns a normal 200 and emits no error; it is invisible per-request. It is caught statistically, from the shape of the traffic (see detection report §11): a scanner shows a high miss ratio (404-heavy), a dumper shows many distinct 200 reads, a walker a dense consecutive id range, and the definitive breach is a 200 the app granted on an object the caller doesn't own.

Detected, live. With the IDOR present, a scan/walk/dump run against the lab fired all four rules and was quiet on a legitimate baseline — scan 203.0.113.61 (90% 404), dump 203.0.113.62 (100% 200, 30 cross-owner reads).

Fix (shipped, commit 5ba2e37). Scope the read to the owner so a not-owned note is indistinguishable from a missing one:

// not-owned => no row => 404, no existence leak
const { rows } = await pool.query(
  'SELECT id,owner_id,title,body,created_at FROM notes WHERE id=$1 AND owner_id=$2', [id, req.user.id]);

Plus authz.granted with owner_id on the read, so the cross-owner detection has its signal. A new integration test proves a note is readable only by its owner (owner 200, another user 404).

Backs detections: the four statistical rules in authorization-detection-mitigation.md §11. Teaching point: the behavioural rules (scan/walk/dump) warn you someone is *hunting*; the cross-owner event tells you whether they *succeeded*.

4. Forward-looking: authorization in the age of AI, MCP & APIs

Not applicable to lab-auth yet (no agent/MCP/tool surface) — the map for when it, or your real app, grows one (catalog group N): re-authorize at the tool boundary per end user (confused-deputy, 61); carry the user's authz down (OBO, 62); bound tokens to an audience/resource (RFC 8707, 67); gate high-impact tool actions behind a human (69 — the agentic analog of step-up); scope retrieval to the caller (RAG, 68); treat agent.action (background runs) as its own privileged surface (70). Emit track('tool.call', { on_behalf_of, decision, tool, target_ref, object_owner }); the detection side is in the sibling report §10.
