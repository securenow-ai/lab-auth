1. Executive summary

The lab now spans authentication, authorization, statistical IDOR, and a real multi-tenant teams / invitations surface (Category O — see §12).

lab-auth's access control is sound (see the code report). The job for SecureNow here was visibility — make authorization decisions observable so an agent can catch someone probing the role boundary, slipping past step-up, or escalating privilege. That is now done end-to-end: the one code gap (decisions not exported) is fixed, four detections are live in test mode (detect-only), and every one fired against real attack traffic generated by the lab's own attack harness.

The three detection tiers (full definition in the generator prompt):

  • Tier 1 — trace-only, no app code. Works the moment SecureNow is plugged in. Here: R-AZ-BOUNDARY

catches *sudden escalation* (403 → 200 on the same restricted route) from HTTP traces alone.

  • Tier 2 — the optional authz.* bridge (one event per decision). Here: role-boundary probing,

step-up bypass, privileged-change fan-out. Needs code finding AZ-1 (shipped).

  • Tier 3 — code fix. AZ-1 (export decisions) and AZ-2 (admin-quorum race) — both implemented.

Top detectable access-control risks, all live:

  1. Role-boundary probing — a member walking /api/admin/* + /api/security → R-AZ-01.
  2. Sudden privilege escalation — a boundary that opens (403 → 200) → R-AZ-BOUNDARY (Tier 1).
  3. Step-up bypass — an admin *session* (not password) hitting the role route → R-AZ-02.
  4. Compromised-admin grant / fan-out — elevation or many targets → R-AZ-03.

12. Teams & invitations — Category O (added 2026-10-20)

The lab grew a real multi-tenant collaboration surface: organizations, invitations, and per-org member roles. Every bug here is invisible in a single request — a wrong-identity invite accept or a self-promotion is one normal-looking call. The routes are built securely (the fix is the default), and every attempt — allow or deny — is exported as a membership.* event, so SecureNow catches the attack shape without a breach ever succeeding. Two detections, test mode, validated live, quiet on the baseline:

6. Mitigation mechanisms

App fix is primary; SecureNow controls are containment. Scoped commands (app already substituted):

# R-AZ-01 confirmed probing — throttle the account's IP on the admin surface only (route+IP), not a global block
securenow rate-limit set --app df7ab010-37ac-4732-88ac-a8ac23afe1a4 --route "/api/admin" --ip <IP> --limit 5 --window 15m
# R-AZ-02 / R-AZ-BOUNDARY — revoke the session, then a 1-hour route+method block as backup
securenow revoke --app df7ab010-37ac-4732-88ac-a8ac23afe1a4 --session <SESSION_REF>
securenow block <IP> --app df7ab010-37ac-4732-88ac-a8ac23afe1a4 --route "/api/admin/users/:id/role" --method PATCH --ttl 1h
# R-AZ-03 confirmed admin takeover — revoke + global block
securenow revoke --app df7ab010-37ac-4732-88ac-a8ac23afe1a4 --session <SESSION_REF>
securenow block <IP> --app df7ab010-37ac-4732-88ac-a8ac23afe1a4 --reason "confirmed admin takeover (R-AZ-03)"

10. Known gaps & SecureNow feature requests

  • BOLA/IDOR (group A): not applicable to lab-auth (no owned business objects). The day a GET /api/x/:id

lands, the Tier-1 object-enumeration rule (distinct :id per route template, in the prompt) and the Tier-2 caller ≠ object_owner rule apply; AZ-3 pre-adds target_ref to the authz events.

track('tool.call', { on_behalf_of, decision, tool, target_ref, object_owner }) + agent.action; detections: deny-clusters per agent/user, privileged tool reached by an under-scoped caller, distinct-object fan-out per agent identity. *Contact the SecureNow team* for the packaged agentic-authz signature set.

  • Cross-session TOCTOU (AZ-2): detection is coarse (fan-out). Primary fix shipped — the atomic

FOR UPDATE transaction; a per-object write-conflict signal is a SecureNow feature request.

11. Statistical IDOR detection — the notes resource (added 2026-10-19)

The lab grew a real owned-object surface: notes, keyed by a predictable integer id (GET /api/notes/:id). It shipped with a textbook IDOR (the row was fetched by id only, not scoped to the owner), which is the point — a *single* IDOR request looks exactly like a normal 200. You can't catch it per-request; you catch the hunting behaviour in the distribution. Four detections, all created in test mode and validated live against a scan → walk → dump attack, all quiet on the legitimate baseline (a user reading their own notes):

The statistical tell, in the dashboard (IP Forensics → Trace Explorer, env test):

  • Scan (203.0.113.61): status mix 2XX 8 (10%) / 4XX 74 (90%) — probing the id space for what exists.
  • Dump (203.0.113.62): 2XX 32 (100%) — pulling every object once the ids are known.
  • Baseline (203.0.113.60, a user reading their own 6 notes): trips nothing — low distinct, zero misses,

owner == caller. That separation is the whole value: behaviour, not a single request.

Instrumentation: rules 1–3 need no app code (pure traffic). Rule 4 needs one event — authz.granted with owner_id on owned-object reads (src/app.js GET /api/notes/:id) — the definitive signal that a 200 was an IDOR and not a legitimate owner read.

Mitigation (app fix is primary): the IDOR is now fixed — the query is scoped to the owner (WHERE id=$1 AND owner_id=$2), so a not-owned note returns 404 with no existence leak (see code finding AZ-5). SecureNow containment while a fix ships: rate-limit the scanner on the :id route, challenge a NAT egress (securenow challenge add --route /api/notes), or block a confirmed dumper. Rule files: rules/lab-auth-idor-scan.sql · rules/lab-auth-idor-dump.sql · rules/lab-auth-idor-sequential-walk.sql · rules/lab-auth-idor-cross-owner.sql.
