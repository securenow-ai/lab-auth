## 1. Executive summary

**Threats modeled 91 · detectable & covered 7 · partial 1 · gaps 0 live · N/A for this app 70 · rules created 6
(all validated firing) · code fixes shipped 2.** The lab now spans authentication, authorization, statistical
IDOR, and a real multi-tenant **teams / invitations** surface (Category O — see §12).

lab-auth's access control is sound (see the code report). The job for SecureNow here was **visibility** — make
authorization decisions observable so an agent can catch someone probing the role boundary, slipping past
step-up, or escalating privilege. That is now done end-to-end: the one code gap (decisions not exported) is
fixed, four detections are live in **test mode (detect-only)**, and **every one fired against real attack
traffic** generated by the lab's own attack harness.

**The three detection tiers** (full definition in the generator prompt):
- **Tier 1 — trace-only, no app code.** Works the moment SecureNow is plugged in. Here: **R-AZ-BOUNDARY**
  catches *sudden escalation* (`403 → 200` on the same restricted route) from HTTP traces alone.
- **Tier 2 — the optional `authz.*` bridge** (one event per decision). Here: role-boundary probing,
  step-up bypass, privileged-change fan-out. Needs code finding **AZ-1** (shipped).
- **Tier 3 — code fix.** AZ-1 (export decisions) and AZ-2 (admin-quorum race) — both implemented.

**Top detectable access-control risks, all live:**
1. **Role-boundary probing** — a `member` walking `/api/admin/*` + `/api/security` → **R-AZ-01**.
2. **Sudden privilege escalation** — a boundary that opens (`403 → 200`) → **R-AZ-BOUNDARY** (Tier 1).
3. **Step-up bypass** — an admin *session* (not password) hitting the role route → **R-AZ-02**.
4. **Compromised-admin grant / fan-out** — elevation or many targets → **R-AZ-03**.

## 6. Mitigation mechanisms

App fix is primary; SecureNow controls are containment. Scoped commands (app already substituted):
```bash
# R-AZ-01 confirmed probing — throttle the account's IP on the admin surface only (route+IP), not a global block
securenow rate-limit set --app df7ab010-37ac-4732-88ac-a8ac23afe1a4 --route "/api/admin" --ip <IP> --limit 5 --window 15m
# R-AZ-02 / R-AZ-BOUNDARY — revoke the session, then a 1-hour route+method block as backup
securenow revoke --app df7ab010-37ac-4732-88ac-a8ac23afe1a4 --session <SESSION_REF>
securenow block <IP> --app df7ab010-37ac-4732-88ac-a8ac23afe1a4 --route "/api/admin/users/:id/role" --method PATCH --ttl 1h
# R-AZ-03 confirmed admin takeover — revoke + global block
securenow revoke --app df7ab010-37ac-4732-88ac-a8ac23afe1a4 --session <SESSION_REF>
securenow block <IP> --app df7ab010-37ac-4732-88ac-a8ac23afe1a4 --reason "confirmed admin takeover (R-AZ-03)"
```
Full toolbox (15 mechanisms) unchanged from the catalog: firewall · signature instant-block · IP block
(global / route+method / temporary) · rate-limit (per-IP / per-route / route+IP) · challenge · auto-block ·
**revoke** · trusted · allowlist · `fp` · **app-config fix**.

## 11. Statistical IDOR detection — the `notes` resource (added 2026-10-19)

The lab grew a real owned-object surface: `notes`, keyed by a **predictable integer id** (`GET /api/notes/:id`).
It shipped with a textbook **IDOR** (the row was fetched by id only, not scoped to the owner), which is the point —
a *single* IDOR request looks exactly like a normal `200`. You can't catch it per-request; you catch the **hunting
behaviour in the distribution**. Four detections, all created in **test mode** and **validated live** against a
scan → walk → dump attack, all **quiet on the legitimate baseline** (a user reading their own notes):

| # | Threat (OWASP/CWE) | Tier | Rule (id) | Signal | Validated |
|---|---|---|---|---|---|
| 1 | ID brute-forcing / id-space scan (API1, CWE-639) | 1 trace | `6ad6adc5…797d` | distinct ids ≥20 **and** `miss_ratio ≥ 0.4` | ip .61 → distinct=80, **miss_ratio 0.92** |
| 2 | IDOR dump / bulk exfiltration (API1, CWE-639) | 1 trace | `6ad6adc7…7982` | distinct **200** objects ≥15 | ip .62 → **distinct_read=30** |
| 3 | Sequential / incrementing id walk (API1, CWE-639) | 1 trace | `6ad6adc9…7987` | distinct ≥12 **and** `id_span ≤ 3×count` | ip .62 → distinct=30, **id_span=29** |
| 4 | Cross-owner access rate — the real breach (CWE-639) | 2 event | `6ad6adcc…798c` | `authz.granted` where `owner_id ≠ caller`, ≥5 | hunter → **cross_owner_reads=36**, 30 objects |

**The statistical tell, in the dashboard (IP Forensics → Trace Explorer, env test):**
- **Scan** (`203.0.113.61`): status mix **2XX 8 (10%) / 4XX 74 (90%)** — probing the id space for what exists.
- **Dump** (`203.0.113.62`): **2XX 32 (100%)** — pulling every object once the ids are known.
- **Baseline** (`203.0.113.60`, a user reading their own 6 notes): trips **nothing** — low distinct, zero misses,
  `owner == caller`. That separation is the whole value: behaviour, not a single request.

**Instrumentation:** rules 1–3 need **no app code** (pure traffic). Rule 4 needs one event — `authz.granted` with
`owner_id` on owned-object reads (`src/app.js` `GET /api/notes/:id`) — the definitive signal that a `200` was an
IDOR and not a legitimate owner read.

**Mitigation (app fix is primary):** the IDOR is now **fixed** — the query is scoped to the owner
(`WHERE id=$1 AND owner_id=$2`), so a not-owned note returns `404` with no existence leak (see code finding AZ-5).
SecureNow containment while a fix ships: rate-limit the scanner on the `:id` route, challenge a NAT egress
(`securenow challenge add --route /api/notes`), or block a confirmed dumper. Rule files:
[`rules/lab-auth-idor-scan.sql`](rules/lab-auth-idor-scan.sql) ·
[`rules/lab-auth-idor-dump.sql`](rules/lab-auth-idor-dump.sql) ·
[`rules/lab-auth-idor-sequential-walk.sql`](rules/lab-auth-idor-sequential-walk.sql) ·
[`rules/lab-auth-idor-cross-owner.sql`](rules/lab-auth-idor-cross-owner.sql).

## 12. Teams & invitations — Category O (added 2026-10-20)

The lab grew a real **multi-tenant collaboration surface**: organizations, invitations, and per-org member
roles (`POST /api/orgs`, `POST /api/orgs/:orgId/invites`, `POST /api/invites/:token/accept`,
`GET /api/orgs/:orgId/members`, `PATCH /api/orgs/:orgId/members/:userId/role`). This is the surface that
dominates modern-SaaS bug-bounty reports, and every bug here is **invisible in a single request** — a wrong-
identity invite accept or a self-promotion is one normal-looking call. The routes are built **securely** (the
fix is the default), and every attempt — allow *or* deny — is exported as a `membership.*` event, so SecureNow
catches the attack **shape** without ever seeing a breach succeed. Two detections, **test mode**, **validated
live** against an invite-rebinding + self-escalation + org-probing attack, **quiet on the baseline** (an owner
invites a member who accepts their own invite):

| # | Threat (OWASP/CWE) | Tier | Rule (id) | Signal | Validated |
|---|---|---|---|---|---|
| 1 | Invite privilege-escalation & identity rebinding (API1/API3, CWE-863) | 2 event | `6ad7a1d8…1c0a` | `identity_match=false` accept, **or** denied admin/owner invite | ip .50 → **rebinding=1** + **escalation_invite=1** (2 rows) |
| 2 | Self-escalation & active-org context tampering (API5, CWE-285) | 2 event | `6ad7a1e0…1c90` | self role-change to admin/owner, **or** ≥3 distinct non-member org switches | ip .60 → **self_escalation=1** + **nonmember_orgs=4** (2 rows) |

**The tell:** no single request is an attack. The **distribution of decisions** is — an invite accepted by the
wrong identity, a member editing their own role upward, one principal poking at orgs it never joined. The honest
baseline (owner → invite → member accepts) returns **zero** rows in both rules.

**Code posture — secure by default (the app fix is primary):**
- **Invite accept is bound to the verified invited identity** — a different signed-in account is rejected, `identity_match=false` (O-75).
- **Invites are admin/owner-only and capped at the inviter's rank**, role server-set and bound to the email, single-use/expiring token (O-72/O-73/O-74).
- **Role change is admin-only, never self-targeted, capped at the actor's rank** (O-79/O-80).
- **Active org is re-verified on every request** — a non-member probe is rejected and exported `member=false` (O-85/O-86).

**Instrumentation:** both rules need the `membership.*` events — `membership.invite.created/accepted`,
`membership.role.changed`, `org.context.switched` — emitted on every attempt from `src/app.js` (shipped).
**Mitigation:** the code already denies every one of these; SecureNow containment on a confirmed attacker is
a scoped block or session revoke on the acting account + IP. Rule files:
[`rules/lab-auth-teams-invite-abuse.sql`](rules/lab-auth-teams-invite-abuse.sql) ·
[`rules/lab-auth-teams-membership-abuse.sql`](rules/lab-auth-teams-membership-abuse.sql). Reproduce the attack
with [`attack-simulation/teams-attack.mjs`](../../attack-simulation/teams-attack.mjs).
